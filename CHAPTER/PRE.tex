\chapter{Preface}
Most monographs and papers present constitutive models analytically and stop there, leaving the implementation to the reader.
That gap matters: implementing a model correctly, especially a complex one, demands both a solid grasp of the theory and a working knowledge of the numerical methods and programming details involved.

This book is a practical guide to implementing plasticity models numerically.

It assumes an undergraduate-level background in linear algebra, numerical analysis, and elasticity, together with some programming experience.
\section{Overview}
The book collects constitutive models for a wide range of materials used in civil and mechanical engineering, covering both uniaxial and triaxial versions.
Implementation details are derived for each model.

The aim is a clear, error-free reference for readers implementing constitutive models in either conventional or novel plasticity frameworks.

The book covers a wide range of models, both in formulation and implementation, and some are lengthy; consequently, it uses a large number of symbols and formulae.

As the title suggests, this is a reference book on constitutive modelling, and it is intended to be self-contained in its treatment of theory.
For practical work, most models come with pseudocode.
Readers familiar with \texttt{C++} and scientific computing will also find core \texttt{C++} implementations, included as references and points of comparison.
The snippets are drawn from \texttt{suanPan} \cite{Chang2022}, and the book can also serve as a program manual.
\section{What Knowledge Is Needed?}
Constitutive modelling is, in practice, the numerical implementation of plasticity theories.
A solid undergraduate grounding in linear algebra is assumed, including comfort with matrix and vector operations and tools such as eigenanalysis.
Familiarity with elasticity, especially small-strain theory, is also expected.
Because plasticity theories can also be read as differential equations, a working knowledge of numerical methods for ODEs and PDEs is required as well.
In most cases, however, basic low-order methods suffice.

For 2D and 3D models, a basic grasp of tensor algebra is also required---by which I mean the first one or two chapters of any tensor-algebra monograph, and nothing more.
Chapter \ref{chap:tensor} summarises the tensor algebra used in this book.
If that chapter makes sense, the required background is covered.
\section{Implementation}
Once the theory is in place, practical questions follow: which language to use, and which programming paradigm to adopt.
\subsection{Which Programming Language?}
\texttt{C} and \texttt{Fortran} dominated scientific computing in its early days.
A large body of libraries written in one or the other still underpins much of the field.

Procedural programming, however, is not always a comfortable fit for scientific computation.
In those languages, vectors, matrices, and tensors are represented by plain arrays.
The corresponding metadata, such as dimensions, can, at best, be stored in \texttt{struct}s.
Operating on arrays is cumbersome and error-prone.
As there is no operator overloading, all linear algebra operations have to be implemented as functions.
The implementation quickly becomes lengthy and hard to read, especially for 2D/3D elements and material models.

\texttt{Fortran} supports matrix operations natively, so the code can be more concise.
Interfacing with external libraries, often necessary for performance, can still be lengthy and tedious because of the required signatures.
The language itself also has a limited feature set.
Writing \texttt{Fortran} is dull---a very subjective opinion---and often amounts to one loop after another.

Three aspects matter when choosing a language for scientific computation.
\begin{itemize}
\item Operator Overloading\\
Operator overloading lets a programmer define how standard operators ($+$, $-$, $*$, $/$) behave on custom types.
That is particularly useful in scientific computing, where operations on vectors, matrices, and tensors are routine.
It lets code resemble mathematical notation, which makes it easier to read and follow.
It can also enable performance optimisations.
Multiplying three matrices, for instance, can be written concisely as
\begin{cppcode}
    mat A, B, C;
    auto D = A * B * C;
\end{cppcode}
Without operator overloading, the same operation must be expressed through function calls.
\begin{cppcode}
    mat matmul(const mat&, const mat&);
    mat A, B, C;
    auto D = matmul(matmul(A, B), C);
\end{cppcode}
\item Ecosystem\\
For standalone material models, a rich ecosystem may not matter much.
At higher levels, however, material models must fit into larger analysis frameworks, where a rich ecosystem can save considerable effort and duplicated work.
\item Multiparadigm Support\\
Multiparadigm support is not strictly necessary, but it is often useful in scientific computation.
In finite element analysis, nodes and elements map naturally onto objects, which makes object-oriented programming (OOP) an obvious choice.
\end{itemize}

This book uses \texttt{C++} for its implementations.
That choice will not suit everyone---preferences vary---but it is a reasonable one.
Other authors have taken a similar view \cite{Poeschel2010}.
The algorithms themselves, however, can be implemented in any language.
\subsection{Notes on Miscellaneous Things}
\subsubsection{State Determination}
The state determination algorithms in this book assume, unless stated otherwise, that local iterations converge.
In practice, they often do not.
Most algorithms solve a local nonlinear system with Newton--Raphson, for instance, and that method is only guaranteed to converge locally.
If the initial guess is too far from the solution, the iteration can simply fail.
Robustness can always be improved by adding safeguards.
The implementations here are therefore references, not gold standards.
\subsubsection{Internal Storage}
Mathematical objects such as tensors can be represented in programs much as they are in mathematics.
Second-order tensors, for example, can be stored as 2D matrices, and fourth-order tensors as four-dimensional arrays.
A complete set of rules can then be defined for tensor algebra.

This approach appears in many other applications.
Under Cauchy stress theory and Voigt notation, however, row and column vectors plus 2D matrices are enough for most models.

All models in this book are implemented that way.
